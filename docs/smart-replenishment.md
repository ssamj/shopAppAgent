# 智能补货单：规则、计划与执行

管理员可以提出“按公司的日常补货规则，生成今天的智能补货单，先给我审核”。模型先检索规则，再依据注册能力提出结构化计划。程序检查计划的来源、步骤依赖及实际执行记录，业务能力读取全量库存与在途、计算、复核并生成待审核建议单。用户不必逐一指定商品。

本功能不创建采购订单、不增加库存、不付款。结果是按本次业务快照生成的建议；实际采购前仍须重新核对。当前只支持单仓、整单采购入库和一套启用的日常补货规则，不含需求预测、部分到货、多仓调拨、自动采购或中断续跑。

## 启用

保持现有配置及业务数据，在本机配置增加 `"replenishment": { "enabled": true }`。依次运行：

```powershell
npm run db:migrate:knowledge
npm run db:migrate:replenishment
npm run knowledge:prepare
npm run replenishment:index
```

随后重启服务。规则检索使用已有本地 E5 模型，不更换聊天模型配置。功能默认不启用，既有商品护理检索索引保持独立。

迁移新增 `business.replenishment_rules` 和 `business.replenishment_snapshots`；不重建业务表，不覆盖用户编排提示词。运行业务角色只能读取规则表，并维护技术快照。快照按账号隔离，有效期30分钟；报告随会话消息保存，可回看当时规则和结果。

## 规则与 RAG 的实际边界

`data/replenishment/daily.md` 是明确标注的虚构教学资料。`manifest.json` 同时维护配套结构化条件：上架范围、可用加在途口径、触发线、目标量和仅供审核的边界。该版本由资料维护者维护原文与参数的一致性，不声称能自动将任意自然语言政策编译为可执行逻辑。

当前 1.1 版本含五部分、29 条业务条款，细化目录范围、SKU 口径、占用、在途状态、边界值、供应商与金额、异常停止、完整计算、复核和审核责任。条款细化不改变原先的触发线 5、目标 10；新增制度必须与实际能力一致，不能只往资料里增加系统尚不支持的采购策略。

已有 1.0 索引的环境升级时，1.1 使用新的规则 ID `daily-replenishment-v1-1`，不覆盖已发布规则。索引新版本后，由资料维护者明确选择启用版本；在同一事务中停用旧版本并启用新版本。确认新版本存在和内容正确后，可执行 `UPDATE business.replenishment_rules SET active=false WHERE id='daily-replenishment-v1';` 与 `UPDATE business.replenishment_rules SET active=true WHERE id='daily-replenishment-v1-1';`。不要删除旧版本；存在多个启用版本时运行器会明确拒绝继续，不按相似度自动决定。

索引阶段核对必要章节，生成条款向量，把原文、规则参数和版本一起绑定到内容哈希。请求阶段根据问题向量计算条款相似度，然后返回同一版本的完整规则包。单个相关片段不能代替整套规则。条款缺失、损坏、模型不一致、规则未启用或存在多个启用规则包时明确失败；相似度不用于擅自裁决规则冲突。

模型根据本轮规则与工具说明提出计划，并在调用中传入原规则参数。业务函数逐字段核对参数，发现改动就失败，不静默修复模型值。原文不能改变权限或授权写入。哈希、来源及 Schema 检查不构成对自然语言理解的完整语义证明。

## Plan → Execute

模型决策可新增 `plan`，包含标题、规则来源 ID 和2～6个步骤。步骤声明 ID、业务名称、能力名与前置步骤。系统协议要求新计划同时给出 `description`（本步业务范围和条件）与 `expectedOutput`（预期取得什么可观察结果）；Schema 保留对没有这两个说明字段的旧计划的兼容。说明不允许预填尚未取得的快照编号，也不替代实际执行或程序校验。只有实际检索到的来源和可用只读计划能力可被采用；最后一步必须是声明 `completesPlan` 的结果能力。

每次调用使用 `stepId` 关联一个待执行步骤。通用运行器核对能力、状态、依赖，以及参数引用是否来自本轮真实工具结果；不按商品、颜色或能力名称写业务分支。一个计划步骤对应一次调用，成功后才完成；失败立即结束，不自动重试或替换计划。沿用最多7次模型决策的上限。

本例注册能力：

| 能力 | 输入与结果 |
|---|---|
| `replenishment_rules_search` | 自然语言问题 → 完整规则、来源、版本与参数 |
| `replenishment_snapshot` | 规则引用与哈希 → 本次全量业务快照 ID |
| `replenishment_calculate` | 快照 ID 与规则参数 → 全量逐规格计算 |
| `replenishment_verify` | 快照 ID → 规则、业务变化和计算复核 |
| `replenishment_report` | 已复核快照 ID → 待审核建议单或无需补货结果 |

这是受约束的单次计划执行，不是任意工作流引擎、通用重规划或恢复系统。页面计划状态来自保存的实际进度事件。业务报告展示具体商品事实；最终文字仅说明完成和审核状态，通用补货规则不能冒充具体商品护理资料。

## 数据与计算

一个 SQL 语句读取完整目录和待到货采购汇总，确保该语句读取同一数据库时点。最多支持5000个规格，查询第5001个用于显式判断超限，不使用普通列表50条限制生成部分补货结果。

可用库存为现货减占用；在途只计算“待到货”采购，已入库不再计入。按当前规则，覆盖量低于5时补到10。所有规格保留检查结果，下架和在途已覆盖等排除原因可以查看。成本按整数分计算，供应商分组合计由业务代码生成。

复核及出单阶段都会重新查询业务数据，并与快照比较；变化时返回 `BUSINESS_CHANGED`。检查仅说明该时点一致，不能保证报告生成后库存不会变化。建议单不锁定库存，也不预留采购额度。

## 验证

`npm run verify:replenishment:unit` 不调用外部模型或数据库，检查补货边界、坏数据、计划来源、依赖、引用和完成条件。

`npm run verify:replenishment:storage` 需明确的隔离配置 `QIHE_CONFIG_PATH` 和 `QIHE_ALLOW_WRITE_TESTS=1`；脚本当前限制在本项目独立演示数据库，事务内夹具回滚。覆盖完整目录、多供应商、无需补货、在途、下架、账号隔离、错误参数、缺少规则、业务变化、提前出单、计算篡改及顾客权限。

真实模型验证另行记录，不能把夹具测试说成模型在所有情况下均理解正确。正常演示仅生成建议报告，不提交采购。
