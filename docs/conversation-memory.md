# 当前会话的上下文与需求记忆

本功能服务于现有商城、经营工作台的多轮聊天。选购需求保存在当前会话中，跨请求和服务重启仍可读取；新会话从空记忆开始。它不实现跨会话的长期用户画像，也不恢复被服务重启中断的 Agent 运行。

## 待确认任务与草稿修订

会话需求和待执行任务分开保存。当前上下文还包含本会话最近的任务草稿：目标 action ID、能力、参数、版本、状态及当时预览。模型根据“改成 5 件，其他不变”等表达，选择目标并提出修改。调用原能力时附带 `revision: { actionId, version }`；`arguments` 为顶层补丁，省略字段保留，数组需提供修改后的完整数组。目标不清楚时应追问，程序不通过关键词判断修改意图。

程序检查归属、版本和状态，先将旧草稿设为 `revising`，阻止旧卡提交，再用合并后的参数重新执行业务预览。成功后在同一事务中将旧版标为 `superseded` 并创建下一版；新旧 action 通过 `draft_id`、`revision` 和 `supersedes_id` 关联。失败则旧版变为 `revision_failed`，不可确认，用户可以明确再次修改或取消。不会在失败后偷偷恢复旧数量的可提交状态。

确认与修订竞争时只有一个合法路径取得执行权。消息处理中不能确认草稿；已经提交的操作不能再当作待确认草稿修改。新版仍需点击确认，创建采购不等于入库或付款。提交沿用业务预览指纹校验和同一 command ID 的幂等处理。不能仅凭聊天里的“已修改”判定业务单据已经改变。

库存查询的结果额外提供 `references`，只记录规格的 ID、名称及关联商品/供应商 ID，供下一轮定位。它不保存可供下轮直接声称有效的库存或价格。引用由业务能力生成，通用上下文读取该字段；运行器不按商品或能力名分流。

已有环境升级运行 `npm run db:migrate:drafts` 后重启智能体服务。此迁移只扩展 action 字段、索引和允许状态，不重建业务表或覆盖提示词。`npm run verify:drafts` 会创建测试采购单，须显式设置独立配置 `QIHE_CONFIG_PATH`、`QIHE_ALLOW_WRITE_TESTS=1` 和该测试账号的 `QIHE_TEST_PASSWORD`，测试结果写入 `output/action-revisions-verification.json`。可用 `QIHE_AGENT_PORT`、`QIHE_BUSINESS_PORT`、`QIHE_WEB_PORT` 将隔离实例与正常开发端口分开；默认仍为 3180、3181、5180。

## 运行路径

1. 消息接口先保存用户消息并建立 run。
2. `memory.ts` 读取当前会话的记忆及尚未处理的用户消息。使用现有模型连接进行一次需求提取；较长的旧会话按最多 16 条用户消息、通常不超过 9,000 字符的批次逐步补齐。
3. 模型只提出需求变更。程序检查 JSON 类型、允许字段、来源消息 ID，以及引用是否确实是该用户消息中的连续原文。校验通过后才更新记忆及消息处理水位；失败立即结束本轮，不自动纠正重试、不继续执行业务工具，旧记忆和处理水位保持。
4. `context.ts` 组合系统协议、业务编排提示词、当前身份与工具目录、会话记忆、商品引用和最多最近 12 条消息。窗口包含本次用户消息，程序会明确标记当前请求。
5. 需求模型结合当前需求与当前身份可用的只读能力说明，提出本轮 `evidenceRequirements`。每组 `anyOf` 是可满足该组的查询依据：`success` 要求成功调用，`empty` 要求成功且结果记录为空。多组需全部满足。模型决定业务上需要哪些依据；`evidence.ts` 校验能力名属于注册的只读能力，并核对本轮实际成功记录。运行器不按商品能力名、颜色或尺码分流。所需依据同时传入决策上下文；准备直接回答时缺少依据，返回 `EVIDENCE_MISSING` 并结束，不补固定查询、不重试掩盖缺失。输入不够时，可用 `needsClarification:true` 明确追问，不声称已取得业务事实。格式不合法、工具执行失败也直接终止；空白回答不能替换成默认“已完成”。业务校验、权限与写操作确认流程保持原职责。

## 需求、摘要和商品引用

结构化字段包括品类、用途、预算上限（人民币分）、排除颜色、偏好颜色、尺码、面料和选购对象。每项保存 `value`、`sourceMessageId`、`quote`。未提及的字段保持；明确修正覆盖同字段；取消条件删除该字段。

询问商品规格与确认选购偏好由模型结合上下文区分。程序不通过关键词或正则判断意图，也不改写通过校验的模型字段值；原始引用单独保留。“这次预算 500 元”只作用于本会话，不自动成为永久用户偏好。

业务含义由商品能力说明声明，例如目录的合计库存不等于某个规格的库存。模型理解仍可能出错；通用检查能核对声明的能力是否实际执行，不能单凭能力名证明每个推荐商品都满足用户语义，具体正确性要结合真实调用参数与结果回归。

需求摘要最多 1,200 字符，仅记录用户目标与约束，不推断“尚未推荐”“已经完成”等执行进度。摘要是模型生成的有损概括；当前明确输入和结构化事实优先，原始消息仍在数据库中保留。引用校验能防止无来源写入，不能单独证明模型对原文的语义理解一定正确，因此需要多轮用例回归。

商品引用从本会话实际保存的助手商品卡中提取。序号保持前端展示顺序，保留商品 ID、名称、来源消息，不把历史价格或库存保存成当前事实。历史商品查询回复中的自然语言也从模型上下文中省略，避免通过“上次说过有货”重新引入旧库存；界面仍保留完整回复。另保存最近查看商品的引用；出现更新的商品列表后，旧的焦点失效。空查询结果也会替换旧列表。最多向模型提供 150 项引用，超过部分不可猜测。

用户明确重新开始选购或忘掉旧需求时，保存重置消息 ID，清空旧条件；此前的聊天和商品卡继续保留供用户查看，但不再进入本次任务的模型上下文。

## 上下文预算与协议

- 历史对话以带来源角色的“历史数据”提供，当前请求单独标明。界面的自然语言回复不直接作为 Agent 决策协议的 assistant 示例，避免模型仿照历史回复跳过 JSON 格式。
- 系统指令、会话记忆、当前用户消息及本轮决策/工具结果受保护；预算不足时先移除较早的历史消息。
- 每次决策输入的应用级预算为 60,000 字符。这是字符预算，不是精确 token 计数；仍受实际模型上下文限制约束。
- 单个工具结果默认压缩至 6,500 字符，按完整行移除，保留有效 JSON、原返回行数与省略行数。前端展示的原始业务卡不裁剪。不能用部分明细推算总金额。
- 若受保护内容仍超出预算，明确返回范围过大的错误，不无声删除本轮必要工具结果。
- 历史商品事实需要刷新；本轮刚查询到的结果可用于本轮回答，无需因“需要刷新历史”反复查询。

## 数据与检查入口

`agent.conversation_memories` 按 conversation_id 保存记忆状态和更新时刻。读取、写入、商品引用查询均检查会话所属账号。数据库原始聊天与模型本次实际输入是不同的数据范围。

`GET /api/conversations/:id/memory` 返回本人会话的需求、摘要与商品引用，供调试和后续教学核对。沿用既有登录会话与 `x-client`，其他账号访问返回 404。

`agent.runs.context_stats` 记录每轮输入字符数、裁剪消息数、记忆版本、最近消息数；不保存系统提示词、模型连接凭据或私有思维链。

## 初始化与验证

已有环境执行 `npm run db:migrate:memory`，再重启智能体服务。迁移只新增记忆表、运行统计字段和消息排序索引；不重建业务库、不覆盖现有编排提示词。全新初始化的 `db/schema.sql` 也包含这些结构。

- `npm run verify:memory:unit`：来源、类型、覆盖、删除、重置、预算与结果压缩，不调用模型。
- `npm run verify:memory:storage`：数据库持久化、越权隔离、失败水位、商品顺序和重置边界；模型响应为夹具，数据在事务内回滚。
- `npm run verify:memory`：真实 HTTP 与模型的多轮选购、条件修正、商品指代、长对话、隔离、重置及管理端查询。会保留验证会话和调用记录，不提交购物或付款。
- `npm run verify:stream:unit` / `npm run verify:stream`：原有模型流、事件续接与确认边界回归。

长对话用例在专用测试会话中插入 20 条明确标注的中性历史夹具，再通过真实模型请求继续选购。它验证原始条件离开最近消息窗口后的恢复，不代表进行了 20 轮真实模型闲聊。运行结果写入 `output/conversation-memory-verification.json`。

每批新增用户消息增加一次需求整理模型调用。旧会话首次补齐可能需要多批；每批校验并持久化后才推进水位。延迟与费用需要结合实际提供方计量，本功能未声称零额外成本。
