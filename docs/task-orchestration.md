# 小型任务编排

可选的补货采购任务把只读补货分析、建议审核、采购草稿确认和实际单据查询连接为一项持久任务。模型依据用户需求选择注册的工作流和节点工具；执行程序管理任务状态、节点依赖、人工等待和调度。当前只支持管理员、单供应商、最多20项需补规格的串行流程。

已有项目保持配置和数据，执行 `npm run db:migrate:workflows`，在自己的本地配置中添加 `"workflows": { "enabled": true }` 后重启智能体服务。还需按[智能补货说明](smart-replenishment.md)启用补货、迁移规则和准备索引。默认不启用任务编排，不覆盖已有业务编排提示词。

服务支持 JSON Schema 结构化输出时，可显式添加 `"strictJsonSchema": true`。该模式为工作流节点使用按可用工具生成的 Schema 和完整 JSON 响应，公开进度仍通过现有事件流显示；普通对话继续使用原有模型流。服务拒绝该模式或结果无效时明确失败，不自动切换协议、重试或修补返回内容。

## 执行过程

管理员可以提出：“按公司规则生成补货建议，先给我审核。我同意后继续准备采购草稿，创建采购单仍需我点击确认，完成后查询实际单据。”模型通过本地注册工具交接任务，原始用户目标由程序读取并保存。

1. `analyze` 节点复用只读 Plan and Execute，生成完整补货报告，保存为 `waiting_review`。无需补货时正常完成。
2. 用户在任务卡审核建议。审核信号绑定任务版本和报告，由同一事务记录审核事件、状态变化和后继待办。
3. `prepare` 节点重新核对原报告的快照、规则及当前业务。变化或过期时原审核失效，形成最新建议后重新等待审核。通过时由模型提出采购调用，程序逐项检查其明细与已审核建议一致，再复用现有 action 预览。
4. `waiting_confirmation` 等待用户点击采购确认卡。准备和最终提交都检查原补货依据；实际写入沿用预览指纹和同一 command ID 的幂等处理。
5. 操作完成的事务同时记录后续待办，`reconcile` 节点使用实际采购结果中的编号查询详情。查询成功以后整项任务完成。创建采购不等于入库或付款。

建议审核允许准备草稿，采购卡确认授权创建单据。绑定任务的采购草稿必须与审核报告一致，需改变明细时先取消任务并重新提出需求；独立草稿继续支持原有参数修订。

## 持久化与调度

`agent.workflows` 保存目标、节点、版本、状态和必要业务结果；`workflow_events` 保存执行和审核记录；`workflow_jobs` 是数据库待办队列；`workflow_runs` 关联每次活跃的 Agent 运行和结构化决策。等待人工时当前运行退出，任务等待状态留在数据库。

轮询器串行领取待办，核对版本后执行注册的节点。重复审核标识、旧版本和非法状态被拒绝或复用原结果；重复 action 完成通知不生成第二个后继待办。单次模型循环最多7次决策，节点在下一次决策前检查5分钟执行预算；每项任务最多12个待办节点。单个模型请求仍使用现有请求超时。

普通 SSE 续接只补收进度事件。任务继续执行依赖持久节点和审核事件。已保存的等待点可以在服务重启后重新加载；运行中断的节点显式标记失败，不宣称支持任意位置的自动恢复。提交结果不确定时保持原 action/command ID 核对，不用新命令盲目重做。

审核与续跑待办采用本地数据库事务。业务 API 写入继续使用自己的事务及幂等键；本地事务不代表跨服务的恰好一次执行。

## 验证

`npm run verify:workflows` 检查审核明细、存储、并发去重、取消、隔离和后继待办。必须显式提供指向独立 episode07 测试库的 `QIHE_CONFIG_PATH` 和 `QIHE_ALLOW_WRITE_TESTS=1`。脚本使用明确标注的状态夹具，不调用模型、不创建采购，测试记录留在隔离库。

真实模型与完整业务验证单独在隔离环境执行。模型格式错误、来源不合法、参数与审核内容不一致或工具失败均明确停止，不自动重试、补默认成功或改写模型值。真实业务写入、确定性夹具检查和教程示意分别作为不同证据记录。
